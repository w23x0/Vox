    `cfg(target_os)` 分流。

## B. 待拍板清单

### B1. 降噪从 DeepFilterNet 换成 RNNoise（事后补票）

**背景**
设计文档写的是 DeepFilterNet，代码里已经是 RNNoise（`nnnoiseless` 0.5.2）。
换的原因是硬的：crates.io 上的 `deep_filter` 0.2.5 **只有 FFT / ERB 前处理原语，
没有神经网络推理、没有权重文件**，压根跑不起来。要用真 DeepFilterNet 得自己塞
ONNX Runtime 或 tract + 外挂几十 MB 权重。

**选项**

| | 方案 | 降噪效果 | 体积 | 工作量 |
| --- | --- | --- | --- | --- |
| a | **维持 RNNoise**（现状） | 稳态噪声够用，突发噪声一般 | +0 MB | 已完成 |
| b | 上 ONNX Runtime + DeepFilterNet | 明显更好 | +30～60 MB，多一个原生 DLL | 2～3 天，且要处理 DLL 分发 |
| c | 干脆不降噪，只靠阀门 | 无 | −0 | 减工作量，但阀门会被底噪骗开 |

**代价**
选 b 要额外背 ONNX Runtime 的跨版本兼容和杀软误报风险，安装包从几 MB 涨到几十 MB。
选 c 会让「开关模式」的音量阀门在有底噪的环境里频繁误触发，等于白送 token。

**我的推荐：a，维持 RNNoise。**
降噪在这个项目里的首要任务是**让音量阀门判断准**，不是追求录音棚音质；而且
真正的噪声抑制服务端模型自己也会做一遍。RNNoise 纯 Rust、权重内嵌、BSD-3 可商用、
帧格式（48 kHz / 480 采样）跟麦克风原生格式天然对齐，性价比最高。
文档已按 RNNoise 写好（`docs/architecture/ARCHITECTURE.md` §9）。

### B2. 「听人说话」实际上只支持 Win11——怎么跟用户讲

**背景**
「听人说话」靠 WASAPI **进程环回**（`VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`），
这个 API 要求系统 **build ≥ 20348**。而零售版 Win10 22H2 的 build 是 **19045**。
结论：**Win10 用户一个都用不了这个功能**（20348 是 Server 2022，普通人不会装）。
代码里已经用 `RtlGetVersion` 做了检测（不用 `GetVersionEx`，那个会被兼容性
垫片骗到只报 6.2）。

**选项**

| | 方案 | 用户体验 |
| --- | --- | --- |
| a | **界面上灰掉 + 一句话说明 + 整机环回兜底** | 功能不可用但有替代品，最不掉脸 |
| b | 只灰掉，鼠标悬停才提示原因 | 干净，但用户会以为是 bug 来问你 |
| c | 安装时就拦下来，Win10 直接说「这功能你用不了」 | 最诚实，但劝退 |
| d | 干掉进程环回，所有人都用整机环回 | 代码简单，但会把**自己的译文语音**一起抓回去翻译，形成回环 |

**代价**
d 是真不行——整机环回会抓到自己放出去的中文译文，翻译自己的翻译，无限套娃
（除非要求用户必须戴耳机，那又变成硬约束）。
c 会让 Win10 用户觉得整个软件都用不了，其实「对外说话」仍然能用。
b 的隐性成本是你的答疑时间。

**我的推荐：a。**
具体做法：设置界面里「听人说话」整块保留可见但控件灰掉，上方一条黄色提示——
> 这个功能需要 Windows 11（或 Windows 10 build 20348 以上）。你现在是 build 19045。
> 「对外说话」不受影响。

再给一个「改用整机环回（需要戴耳机）」的复选框作为兜底：勾上就抓整机声音，
同时在旁边写死一句「**必须戴耳机**，否则会把译文自己翻译一遍」。
代码里 `unsupported_message()` 已经是这个思路（提到两个 build 号 + 建议整机环回兜底），
只要 UI 照着显示就行。

**需要你确认的**：兜底的「整机环回」这一版要不要做？不做的话我就只留灰掉 + 提示。

### B3. 安装程序：NSIS 还是 MSI，要不要默认提权

**背景**
Tauri v2 两种都支持。VB-CABLE 的静默安装**需要管理员权限**，
而这一步是「听人说话」和「对外说话」的前置条件（要往虚拟麦克风灌声音）。

**选项**

| | 方案 | 提权 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| a | **NSIS + 安装器提权，程序本身不提权** | 只在装的时候 | 装完就能用；日常运行是普通权限（安全） | 安装时弹一次 UAC |
| b | NSIS，全程不提权，VB-CABLE 交给用户手动装 | 无 | 装得最干净 | 用户得自己去官网下载、双击、点下一步，劝退率高 |
| c | MSI（WiX） | 同 a | 企业环境好推（组策略、静默部署） | 打包更麻烦，Tauri 的 MSI 定制能力弱 |
| d | 程序本身也常驻管理员 | 全程 | 当前功能没有必要收益 | 安全上不好，且每次启动弹 UAC |

**我的推荐：a（NSIS，安装器提权，主程序普通权限）。**
理由：一次 UAC 换「装完即用」，这是国内工具类软件的标准做法。

**需要你确认的**：接受一次 UAC 吗？

### B5. 源语言要不要给用户选（自动识别靠不靠得住）

**背景**
旧 Python 版**从来没发过任何源语言字段**——`session.update` 里只有目标语言，
靠模型自己认你说的是什么语言，而且**就这样上线用了很久没出问题**。
（我把旧项目全文搜了一遍 `source_lang` / `source_language`，一个都没有。）

**选项**

| | 方案 | 效果 |
| --- | --- | --- |
| a | **完全不给选，靠自动识别**（沿用旧版） | 设置界面最干净；中英混说也能处理 |
| b | 给一个「源语言」下拉，默认「自动」 | 多一个旋钮；识别抽风时用户能自救 |
| c | 强制选源语言，不给自动 | 最稳，但每次切换说话语言都得回来改设置 |

**✅ 调研已确认（2026-08-05，官方文档）**

字段名和行为都查到了，b 不再有技术风险：

- 字段是 **`input_audio_transcription.language`**（在 `session` 里，不在 `translation` 里）。
- 官方原话：**"默认不填写，此时模型会自动识别源语种。"** → 自动识别是官方支持的正路，
  不是旧版蒙对的。
- 可选值就是那份 60 语言代码表（源、目标共用一份）。
- **额外好消息**：转写事件会**回报识别到的 `language`**。
  也就是说"识别错了"这件事**程序能看见**，不是黑盒。

**代价**
a 的风险场景：**你说中文但被识别成日语**——常见于只说一两个词、或者中日夹杂
（说「はい」「OK」这种）。这时输出会乱，而用户**没有任何手段自救**。
b 的成本现在**确认很低**（一个下拉框 + 一个已知字段名），官方明确支持。

**我的推荐：a 起步，b 作为后备。**
先按旧版的做法上（已经验证能用），设置界面**不出现**源语言。
如果实测发现短句误判明显，再加 b——现在字段名已经查清了，加起来是十分钟的事。

**顺带一个便宜的中间方案**：既然服务端会回报检测到的语言，
可以先**不给下拉框，但在字幕旁边小字显示识别到的语言**。
用户看到"识别成日语了"就知道该说慢点/说长点，而我们不用加设置项。
这个要接 `conversation.item.input_audio_transcription.*` 事件（现在没接）。

**需要你确认的**：同意先不给选吗？要不要做那个"显示识别到的语言"的小字？

> ✅ **已拍板（2026-08-17）**：**两个都做** —— 加源语言下拉（现有 13 种 + 自动识别，
> 不引入 60 种大表），也做「识别成 X 语言」的小字。已实现，见「已拍板」第 13 条。
> 小字只在**自动识别**（没手动锁源语言）时显示，锁了就没什么可提示的。

### B7. 空闲超时和心跳（附带项，一并定了省事）

**背景**
「听人说话」可能开着一整晚没人说话，「对外说话」也可能长时间没开麦。
如果服务端有空闲超时，连接会被静默掐掉。
代码现在**没有主动心跳**，只靠 tungstenite 自动回应服务端的 Ping。

**选项**

| | 方案 | 代价 |
| --- | --- | --- |
| a | **不主动心跳，断了就靠重连退避补上** | 最简单；断线瞬间的第一句话会丢 |
| b | 空闲时每 N 秒发一帧静音音频当心跳 | 连接稳；但**静音也算 token**，白烧钱 |
| c | 空闲时定期发 WS Ping 帧 | 不烧 token；但要确认服务端认不认 |
| d | 空闲超过 N 分钟主动断开，用户一开麦再连 | 最省；但第一句话有握手延迟（约 1 s） |

**✅ 调研已确认（2026-08-05）：这条基本不用操心了**

- **查不到任何空闲超时的说法。**
- **但有一个硬上限**：官方原话"**单次会话最长可持续 120 分钟**，
  达到此上限后服务将主动关闭连接"。所以长挂的连接**一定**会被踢。
- **好消息：现在的代码已经扛得住。** 服务端主动关闭走 `Incoming::Closed`，
  而 `Closed` **完全不经过 `is_fatal_error()`**（那函数只判 `error` 事件的 code），
  所以落在可重试分支 → 400 ms 起步的退避重连。
  代价是两小时一次、几百毫秒的字幕断档，挂机时基本察觉不到。

**所以 c（30 秒 WS Ping）现在看是多余的**——不是有害，是没必要：
超时不存在，120 分钟是硬上限，Ping 也留不住。

**我的推荐：只要 a（现状），不做 c。**

**需要你确认的**：同意"什么都不加、就靠现有重连"吗？
（如果你更保守，加 30 s Ping 也无害，就是多几行代码。）

### B8. token 用量只记总数，可能算不准钱

**背景**
✅ 已核实官方 `usage` 结构，除了我们在读的三个总数，还有：

```json
"input_tokens_details":  { "text_tokens": 20, "audio_tokens": 27 },
"output_tokens_details": { "text_tokens": 2,  "audio_tokens": 7  }
```

**我们没读这两个细分字段。** 而官方计费口径里，音频和文字**不是一个价**：
LiveTranslate-Flash 的音频按**输入 7 token/秒、输出 12.5 token/秒**折算，
文字部分（开了源文 ASR 才有）按输出文字价计。

所以把 input + output 加成一个 `total_tokens` 再乘一个单价，**算出来的钱是错的**。

**选项**

| | 方案 | 代价 |
| --- | --- | --- |
| a | 继续只记 token 总数，**界面不显示钱** | 零成本；token 数是准的，只是用户得自己去账单看钱 |
| b | 读细分字段，按模态分别记账，界面估算金额 | 准；但要动 `usage.rs` 的结构（多 4 个计数器），还要维护单价表 |
| c | 读细分字段但**只存不算钱**，界面仍只显示 token | 折中；数据先攒着，以后要算钱不用重新攒 |

**代价**
b 的隐藏成本是**单价表会过期**——阿里云调价我们不会自动知道，
显示一个错的金额比不显示更糟。

**我的推荐：c。**
读进来存着（`UsageLedger` 加几个字段），**界面只显示 token 数，不显示金额**。
理由：token 数是客观的、不会过期；金额需要维护单价表，容易变成错误信息源。
用户想知道花了多少钱，让他去阿里云账单看——那才是权威。

**需要你确认的**：同意"只显示 token、不显示金额"吗？细分字段要不要现在就存？

### B9. 🔴 默认模型的流式字幕可能一直没生效（调研新发现，优先级最高）

**背景**
官方《LiveTranslate 服务端事件》里，流式文字事件叫 **`response.text.text`** 和
**`response.audio_transcript.text`**（字段 `text` + `stash`）。
那份列表里**根本没有** `.delta` 结尾的文字事件。

而我们的解码器**只匹配 `.delta`**。默认模型正是 LiveTranslate
（`qwen3.5-livetranslate-flash-realtime`）。如果官方文档准确，那么默认模型上：

- ✅ 语音、✅ 整句字幕、✅ token 用量 —— 都正常（这些事件名两家一样）
- ❌ **流式字幕不生效**：字只在整句说完时一次性蹦出来，不会一个字一个字爬

**这个缺口是从旧 Python 一路继承的**，不是移植时写坏的——旧版 handler 字典里
也只有 `.delta`，而旧版默认模型也是 LiveTranslate。

**但静态证据是矛盾的**（所以我不敢直接下结论）：
旧版 overlay 的注释写着它接的是"增量翻译流的当前全文（**会随流增长，或被订正**）"，
还逐字打生戳做动画。"**被订正**"正是 `stash` 的语义——
纯 `.delta` 累加只增不改，`.done` 兜底也不会产生订正。
所以要么服务端**两种名字都发**（官方文档没写全），要么那个逐字动画其实一直是白做的。

**选项**

| | 方案 | 代价 |
| --- | --- | --- |
| a | **加 `.text` / `.audio_transcript.text` 分支，顺带读 `stash`** | 纯增量，猜错也不亏（分支不触发而已） |
| b | 先拿真 key 抓一次报文，再决定 | 最准；但要等，而 `protocol.rs` 现在有人在写 |
| c | 不管，反正整句能出 | 省事；但流式字幕是这产品的核心体验，等于砍掉一半 |

**我的推荐：a，而且现在就做。**
加两个 match 分支 + 读 `stash`，是**严格增量**的改动：
LiveTranslate 如果发 `.text`，流式字幕当场就活了；旧 `.delta` 事件仍兼容。

实现要点：`.text` 事件的正确渲染是 **`text + stash`** 拼起来，
其中 `text` 是已确认前缀、`stash` 是可能被改写的尾巴。
这和现在 `parts` 的只增不改假设不一样，**不能简单 `push_str`**——
`text` 是累积确认值（要**替换**而不是追加），`stash` 每次都要丢掉重来。

**需要你确认的**：
① 同意现在就加 `.text` 支持吗？（这要动 `protocol.rs`，得通知写它的那个对话）
② 什么时候能拿真 key 抓一次报文？这是所有未确认项里**唯一影响可见功能**的一条。

### B10. 要不要用官方的热词表（`translation.corpus.phrases`）

**背景**
调研时发现 LiveTranslate 有个我们完全没用的字段：
**`translation.corpus.phrases`**，是个"原文词 → 指定译法"的映射表。

对 VRChat 这个场景**特别对症**：玩家 ID、游戏术语、圈内梗，
交给模型自由翻译基本都会翻歪（人名被意译、术语被直译）。

**选项**

| | 方案 | 代价 |
| --- | --- | --- |
| a | 不做 | 零成本；专有名词继续翻歪 |
| b | 设置里加一个"术语表"，用户自己填几行 | 一个多行输入框 + 存进 settings；热更新时一起发 |
| c | 内置一份 VRChat 常用词表，用户可增删 | 效果最好；但要我们维护词表，而且口味因人而异 |

**代价**
b 的实现量很小：settings 里加一个 `Vec<(String, String)>`，
`session.update` 里带上。产品只接 LiveTranslate，因此不用维护第二套术语注入逻辑。

**我的推荐：b，但排到第一版之后。**
当前两条流水线主链路已经跑通，加这个属于锦上添花。
不过**建议现在就在 settings 结构里留好字段**（空的 `Vec`），
免得以后加字段又要动一遍序列化和迁移。

**需要你确认的**：这版做不做？要不要现在先在 settings 里占个位？

**背景**
`catalog::AUDIO_OUTPUT_LANGUAGES` 是**全局唯一一份**，29 个代码。
✅ 已核实：这 29 个对 `qwen3.5-livetranslate-*` **完全正确**。

| c | 干脆把老模型从目录里删掉 | 最省事；少一个选项，但那模型确实没什么用了 |

**我的推荐：c，如果你不需要那个老模型的话。**
它比 3.5 差、语言还少，留着只是多一个能踩的坑。
如果要留，就做 b。

**需要你确认的**：老模型 `qwen3-livetranslate-flash-realtime-2025-09-22` 还要吗？

### B13. Discord 专属增强适配（**第二阶段预研，尚未拍板**）

> 初心是让 Vox「和 Discord 高度配合」。完整摊开了方向、能力边界、延迟与工程代价，

**待你确认的分叉（Q1，影响整个设计）**

- 「按用户独立分派、每人各自 translate」。（**只有 Bot 能做**——你已经明确这个方向。）

- **D1 opus 解码**：Discord 语音是分用户的 20ms opus 帧。要不要**引 `opus` crate**（打破

## C. 后端契约

> 事件通道名和 `kind` 取值来自 `crates/vox-core/src/event.rs`，前端按这里的契约消费。

### C1. 事件通道

后端 → 前端**只有一个通道**：

```
vox://event
```

所有事件都从这个通道来，用 `kind` 字段区分。**不要再开第二个通道**，
前端一个 listener 全收。

### C2. `kind` 取值（来自 `event.rs`，权威）

serde 用 `#[serde(tag = "kind", rename_all = "snake_case")]`，所以线上的 JSON 是
扁平的、带 `kind` 标签：

| `kind` | 载荷字段 | 什么时候来 |
| --- | --- | --- |
| `settings_changed` | `settings`（完整 `Settings`） | 任何设置变了。**前端不要自己算新状态，等这条** |
| `pipeline_state` | `pipeline`, `state` | 某条流水线换阶段 |
| `gate_status` | `pipeline`, `status` | 阀门状态。**高频**（音量条靠它），前端要节流 |
| `subtitle_delta` | `track`, `text`, `done` | 来了新字幕。`text` 是**整句累计**不是增量片段 |
| `subtitle_cleared` | `track` | 该清空这一行了 |
| `usage_changed` | `usage`（完整 `UsageLedger`） | token 涨了 |
| `mic_active` | `active` | 开麦 / 闭麦（悬浮窗的指示灯靠它） |
| `devices_changed` | 无 | 设备列表变了，前端该重新拉一次快照 |
| `notice` | `notice` | 有话要跟用户说 |

枚举取值（**照抄，别自己猜大小写**）：

- `pipeline`：`speak` / `listen`
- `track`：`speak` / `listen`
- `state`：`idle` / `starting` / `ready` / `active` / `reconnecting` / `failed`
  - `is_running()` 只有 `idle` 和 `failed` 是 false，其它都算「在跑」
- `notice.severity`：`info` / `warning` / `error`

### C3. Tauri 命令（**提案**，待前后端确认）

原则：**前端不持有状态**，只有「拉快照」和「发指令」两类调用。
一切状态从 `Snapshot` 来，一切变更靠事件推回来。

| 命令 | 参数 | 返回 | 对应内核方法 |
| --- | --- | --- | --- |
| `get_snapshot` | — | `Snapshot` | `Runtime::snapshot()` |
| `update_settings` | `patch: Settings` | `Settings`（normalize 后的） | `Runtime::update_settings()` |
| `set_api_key` | `key: String` | — | `Runtime::set_api_key()` |
| `start_pipeline` | `pipeline` | — | `Runtime::start()` |
| `stop_pipeline` | `pipeline` | — | `Runtime::stop()` |
| `toggle_pipeline` | `pipeline` | — | `Runtime::toggle()` |
| `reset_usage` | — | — | `Runtime::reset_usage()` |
| `refresh_devices` | — | — | 外壳重新枚举后 `Runtime::set_devices()` |
| `clear_notices` | — | — | `Runtime::clear_notices()` |
| `install_virtual_cable` | — | 进度靠 `notice` 事件推 | 外壳侧，下载 + 静默安装 |
| `set_overlay_visible` | `visible: bool` | — | `SubtitleView::show/hide` |
| `open_url` | `url: String` | — | 「去领密钥」按钮直达 DashScope 控制台 |

**几条硬规矩**（都是内核已经强制的，前端别绕）：

1. **`update_settings` 返回的是 normalize 之后的值**。前端必须用返回值（或等
   `settings_changed` 事件）刷新界面，**不能假定自己发出去的值就是最终值**——
   越界的会被夹回来（比如阀门阈值 5.0 会变成 0.2），非法音色会被换掉。
2. **`api_key_configured` 是布尔**。快照里**永远不会**出现密钥明文，
   前端不要试图回显密钥。
3. **`headphones_advised` 由后端算**（两条流水线都在跑时为 true），
   前端只负责显示提醒，别自己判断。
4. **`get_snapshot` 是唯一的真相来源**。前端不要缓存 `Settings` 再自己改字段——
   收到 `settings_changed` 就整个换掉。

### C4. 还没定的接口
