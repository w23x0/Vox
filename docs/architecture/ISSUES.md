# SPEC / 规约问题台账（ISSUES）

> **定位**：施工期发现的**规约矛盾、测试不合理、规则两解**——写进这里，等人拍板，
> **不许自行决定后当既成事实写进代码或文档**。
>
> 出处（2026-10-12）：借鉴“规则驱动施工”工作流（conformance 规则表 + 可解析分数 +
> 无人值守循环那一套）。结论：**只移植它能在本仓库机器判定的那一半**——
> 差分金样场景就是我们的 conformance 规则（`golden.rs::SCENARIOS` 每条配一份 `golden/*.txt`），
> `tools/audit.sh` 就是审计输出（一屏、可解析、含退步检测）。不移植的：编译器式完备
> MUST 规约（我们没有这样的 spec，产品行为大量是 SHOULD 级体验与硬件事实）、
> 以及无人值守多轮循环（门下有四道人工闸：单文件单 owner / 收口看门禁 / 推送前门全绿 /
> 破坏性操作先问——无人值守会全绕过，而本项目最严重的历史事故恰是“无证据的全绿”）。
> 本文件承载原工作流里 `spec/ISSUES.md` 那一格。

## 条目格式

```
ISSUE-<三位> | <关联：rule-id / 施工单 / symbol> | <问题一句> | <选项与代价> | 状态：等人类确认
```

关闭时补：`结论: …（去处: <文件>，2026-…）`，条目不删。

## 什么该进、什么不该进

**该进**：同一份规约两条规则矛盾；测试期望输出无法从规约推出、只能从实现反推
（那不是测试，是快照）；一条规则两种合理实现、选哪个改变对外行为；审计脚本判不了
但违反红线的行为（例：为了让 audit 变绿而改测试——见下）。

**不该进**：只是还没做的（→ plans/）；产品方向没定（→ B 区）；已解决的（→ 回填）。

## 工作流红线（从 RULES.md 收敛而来，audit 文化下必须钉在这）

1. **不许为了让 audit 变绿而改测试或金样**：金样 diff 失败 = 实现错了或规约变了，
   两条路都必须先在本文件（或 DECISIONS）留痕等人确认，不许直接动 `golden/*.txt` 或
   `*_matches_its_golden` 测试。例外只有一个：规约本身经裁决变更，此时同步改金样并
   在 commit message 注明 ISSUE/DECISION 编号。
2. **不许按输入特判**：`speak_44k_*` 那种“按采样率跳过算子”是**能力位事实降级**
   （rate 不支持 = 真降级），受保护；禁止的是“按这份输入的形状返回写死的结果”
   （对测试输入硬编码、按文件名/场景名分支）。判据：同一类**没见过的输入**走同一路径
   也必须对金样成立。
3. **audit 输出里的每个数必须来自真跑**：脚本只跑 `cargo test/clippy/fmt` 与 `npm verify`，
   不写“拍脑袋分”。`note` 行明确列了哪些项**不进** audit（不可机器判定），
   不许为了让分母好看把它们塞进去凑数。
