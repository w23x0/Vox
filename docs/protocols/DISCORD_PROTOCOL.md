## 1. 为什么现在要碰 Discord

Vox 现有的「听人说话」用 WASAPI **进程环回**抓指定程序的声音（`Discord.exe` 那一整棵进程树），
只能拿到整摊**混合了所有人的**混音，而且**抓不到是谁在说话**。只要目标是「分清频道里的每个人、
给每个人独立字幕 / 独立翻译方向」，进程环回就**够不着**——能拆出每人的唯一途径是
Discord Bot 的**语音音频流接收**。

- ⚠️ **没人拍板过**：需求到底要不要做到「按人独立」这一层。如果只想把「频道里所有说话声」翻译成
  一条，进程环回在 Win11 已够用（但那不做身份）。**这个分叉决定整个设计。**

## 2. 核心形态（当前理解 · 非定论）

> 我目前的理解，还需要你验证：**Bot 只当一只「耳朵」，不替你「说话」。**

```
  别人在频道里说话
        │
        ▼
  ┌────────────────────────────────────────────┐
  │ 你的 Tauri App（本地跑，内嵌 Bot 客户端）           │
  │   ├─ Discord Gateway：连接 / 心跳 / 事件          │
  │   ├─ Discord 语音连接：把 Bot 弄进「当前语音频道」    │
  │   └─ 逐人收 RTP ─▶ opus 解码 ─▶ 每人一条 16 kHz PCM     │
  │               │                               │
  │               ▼                               │
  │   vox-core 现有翻译流水线（复用「听人说话」）               │
  │   → 每人一份字幕 / 译音                          │
  └────────────────────────────────────────────┘

  你自己说话（不走 Bot）
     └─ 麦克风 → RNNoise → 翻译 → VB-CABLE → 你的真实 Discord 账号发出去
```

要点：

- **Bot 只听**：收「别人」的语音做翻译 / 字幕 / 统计。**你发话**仍用你自己的真实 Discord 账号 +
  VB-CABLE，Bot 不碰「替你发音交给 Discord」这层（避免身份 / 权限 / 音频回灌难题）。
- **单频道**：一次只能把 Bot 放进一个语音频道当耳朵。Discord Bot 没有「全局监听所有频道」的
  超能力——它只接收它**被连进去**的那个频道里的音频。
- ⚠️ **这是预判，未确认**「Bot 只当耳朵」这个位置技术上是否锁死。

## 3. 能力边界（把「能做到」和「做不到」分开）

| 能力 | 进程环回（现状） | Bot 音频流 | 归属 |
| --- | --- | --- | --- |
| 听见频道里别人说话 | ✔ 混音整体 | ✔ 分开每个用户 | 混合 → 可分 |
| 知道是谁在说话 | ✘ | ✔（Discord 带来源） | 依赖 Bot |
| 知道切了频道 / 谁进出 | ✘（只能从音量猜） | ✔（`VOICE_STATE_UPDATE` 事件） | 依赖 Bot |
| 按用户分开独立翻译 / 字幕 | ✘ | ✔（每用户一条流） | 依赖 Bot |
| 你自己发言让别人听懂 | 你的麦克风 + VB-CABLE | （Bot 不建议走） | 不变 |

**结论**：你已经指出并且我认同——**「按人独立」只有 Bot 一条路。** 进程环回唯一的胜点是
「现在就能跑、零接入」，但拿不到身份与频道归属，它**不是** Bot 的替代方案。

## 4. 部署形态 / 延迟（把方向钉死的关键段）

### 4.1 部署：Bot 跑在使用者自己电脑上的「本地服务」

- **运行环境**：在 Tauri（Rust）后端起一个**本地 Bot 进程**，随应用进程一起跑（复用现有的
  DPAPI、WebSocket 传输，跑在 Windows 上）。
- **应用形态**：**客户端 Bot**——它在你的电脑上、在你的进程里收你的。不是集团/云端部署。
- **依赖**：需要你在 Discord Developer Portal 上创建一个 Application，拿到一个 **Bot Token**
  （本地保存，走 DPAPI，不并入现有的 API Key 体系）。
- **权限范围很小**：只求 `connect`（加入语音频道）这一项视图权限。不需要发消息 / 读成员等
  乱七八糟的权限。

### 4.2 延迟分解（翻译管线叠加之前，Bot 这一侧引入的量）

| 环节 | 典型量 | 备注 |
| --- | --- | --- |
| 别人发声 → Bot 收到 | +约 40–70 ms | 由本机到 Discord 服务器区域的位置决定 |
| opus 解码（RTP → 48 kHz → 降到 16）| +5–10 ms | 本机 CPU，毫秒级 |
| **喂进现有翻译 WebSocket** | =**这条链路原有的延迟（主导项）** | 翻译往返本身 ≈600–1200 ms |
| 译音返回到你的界面 / 耳机 | +5–15 ms | 播放侧 |

**结论**：Bot 这一路（网络接收 + 解码）只增加约 **+20–35 ms**，翻译本身才是大头（≥600 ms）。
所以「Bot 作耳朵」对体感延迟影响可忽略，**瓶颈不变仍是翻译往返**。

- ⚠️ **仍待确认**：不同服务商（阿里百炼 vs Gemini）的延迟差——但那是翻译链路本来的事，
  Bot 不会额外叠加多少。

## 5. 关键工程决策点（⚠️ 全部待定，未拍板）

### D1. 用什么解 opus？（最硬的一道墙）

Discord 收进每个用户的音频是 **20 ms 一帧的 opus**（分片发送）。要拿到每人独立 PCM，必须解码 opus。

| | 方案 | 理由 / 代价 |
| --- | --- | --- |
| a | 用现成 **`opus` crate**（link libopus） | 快、稳，把手腾出来做身份 / 字幕 / 翻译。**但新引外部依赖**，Vox 目前音频链路 0 编解码依赖，`vox-dsp` 只有 RNNoise（`nnnoiseless`）+ resample，没有 opus。 |
| b | 自研 opus 解码 | 从零写 opus 解码器是数周 + 体量、且极容易出错。只有想要全离线 / 极致精简依赖链才值得。 |

> ⚠️ **未定**。推荐 **a**，但「要不要为这个打破无额外依赖」也属于你才能拍。

### D2. 用什么方式做 Discord 客户端 / 协议层？

- a | 用现成 Rust crate（`serenity` / `songbird` / `twilight`） | 网关、语音、事件都现成、维护好；但引入依赖、增大体积，且**要验证它们是否真的支持「接自己 Bot Token、接收每个用户的语音流」**（`songbird` 主要是发音乐到频道那一路，接收旁路要确认）。
- b | 自己精简实现 Gateway（心跳 / 鉴权）+ RTP / opus | 依赖最干净，但要额外维护大量协议细节，工作量大。

> ⚠️ **未定。** 这些 crate 对「接收每用户语音」的成熟度我要先调研再下结论。

### D3. 用户自建 Bot 的入门门槛

方案一贯用**本地 Bot**，意味着每个用户要先自己在 Discord Developer Portal 建一个
Application、拿 Token、填进设置页。这是就此方案的一个「信任或体力成本」。
对于面向大众的产品，要把这一步做**向导化**（在设置页带链接、步骤化引导）。

### D4. 对外说话那半要不要动

现状（VB-CABLE + 真实账号）**其实是方案里最不需要碰的**——Bot 不参与「你说话」这条路。
⚠️ 这只是我认知，未拍板确认：「Bot 只当耳朵、你自己说话仍走真实账号」是否也是你想要的
第一版效果。

## 6. 我建议的实施顺序（⚠️ 还是建议，未拍板）

> 这不是拍板，是「先动哪里」的排序建议。每一步都标了对应的拍板项。

1. **先定「范围分水岭」**（对应 Q1）：第一期是「Bot 当耳朵、频道所有说话混一股翻译成」，还是
   「按用户分派、每人各自 translate」？变动整个设计面，必须先拍。
2. **先决 opus 方向（D1）**：第一座待定延迟的墙。
3. 若走 Bot 深度：先做**一个 proof-of-concept**——做进 Gateway hello → 鉴权 → 加入 / 退出频道 →
   收到第一帧用户音频 → 解码成 PCM。全放在新 crate `crates/vox-discord/`，只跟现有 `vox-net`
   （纯 WebSocket）对接，**不侵入**主内核。
4. 字幕落到前端：**只复用现有的 `vox://event` 单一事件通道**，不新增通道。

## 7. 与现有架构的接合（预想，没动代码）

- **新 crate 位**：`crates/vox-discord/`——只做「Discord 协议连接 + 语音包收 + opus 解码成
  每用户 16 kHz PCM」；它把自清干净的 PCM 交回现有流水线。**不动** `vox-audio-win` 的麦克风 /
  VB-CABLE / 进程环回那套。
- **只新增一个「听人」源**：在 `vox-core` 录制源类型里加 `DiscordVoice` 同类，后端走 Bot，
  复用「听人说话」翻译链。**你说话的链路**（VB-CABLE → 你的真实账号）不动。
- **决定不动**：音量阀门、RNNoise、16 kHz 约定、`snake_case` 字段、单事件通道，全部不变。
